# 単一ファイル梱包

なでしこ1で好評だった「作ったものをそのまま渡せる」を取り戻す部分です。
設計の基準はリポジトリ直下の `AGENTS.md` で、本ドキュメントはそこから
単一ファイル梱包に関する節を独立させたものです。運用手順の詳細は
`docs/bundle-resources.md` も参照してください。

```bash
gonako build かんたんゲーム.nako3 --resource ./images --out かんたんゲーム
```

構成はシンプルに、**ランタイム本体の末尾にペイロードを追記**する方式にします。

```text
[ gonako ランタイム本体 (通常のGoバイナリ) ][ ペイロード ][ フッタ(マジック+長さ) ]
```

- ペイロードは `IR + リソース` をまとめたzip
- 起動時に自分自身（`os.Executable()`）の末尾を読み、フッタがあれば同梱モードで動く
- リソースは `internal/bundle` の仮想ファイルシステム越しに見せ、
  **なでしこ側からは通常のファイル読み込み命令と同じ書き方**でアクセスできるようにする
- 開発中（同梱なし）は実ファイルを読むので、書き換えなしで同じコードが動く

クロスコンパイルは `GOOS` / `GOARCH` を指定してランタイム本体を用意しておき、
それにペイロードを追記するだけなので、**ビルド機にGoツールチェインが要りません**。

## 出力先の置換と権限

梱包は出力先と同じフォルダの一時ファイルに書き出し、書き込み・同期・
クローズが成功した場合だけ出力先を置き換えます。梱包や置換に失敗した
場合は旧出力を保持し、一時ファイルを削除します。

出力先がシンボリックリンクなら、**リンク自体を通常ファイルに置き換えます**。
リンク先のファイルは更新しません。リンク先を更新したい場合は、その実体の
パスを出力先に指定してください。

置換には出力フォルダへの書込権限が必要です。既存ファイルだけが書込可能でも、
フォルダが書込不可なら梱包は失敗します。Windowsで実行中の出力ファイルを
置換する場合も失敗することがあるため、そのアプリを終了してから梱包してください。

既存出力のパーミッションは維持し、新規出力にはumaskを反映します。
一方、旧ファイルの所有者・ACL・拡張属性は引き継がず、新規作成時の規則に
従います。ハードリンクで同じ旧ファイルを参照する別のパスも更新しません。

強制終了などで残った `.gonako-build-*` は、通常の隠しファイルと同じ規則で
リソースから除外します。

## ペイロードの中身

ペイロードのzipには `manifest.json` を入れ、**アプリの種類**を持たせます。

| 種類 | 起動時の動作 | 中身 |
|---|---|---|
| `nako3` | 同梱したプログラムを実行する | `program.ir.json` + `resources/` |
| `html` | 同梱した開始ページをWebViewで開く | `resources/`（`entry` が開始ページ） |

マニフェストのない古いバンドルは `nako3` として読みます（後方互換）。

リソースの入れ方は2通りあります。`gonako build --resource ./images` は
**フォルダ名を残して** `resources/images/…` に入れるので、開発中に
`「images/a.png」を開く` と書いたコードがそのまま動きます。GUI版の
「フォルダを実行ファイルに変換」（→ `docs/gonako-gui-editor.md`）は逆に
**フォルダの中身を平らに**入れるので、`「data/x.csv」を開く` がそのまま
動きます。どちらも「開発時に書いたパスがそのまま通る」という一点に
揃えてあります。

## リソース内のシンボリックリンク

既定では、リソースフォルダの外を指すシンボリックリンクを **エラーに
して拒否** します (Issue #187)。外部のファイルがうっかり配布バイナリへ
取り込まれてしまうのを防ぐためです。

意図的にリンク先も梱包したいときは `--include-symlink` を指定します
(Issue #263)。リンクは必ず **リンク名側のパス** (例: `resources/res/link.txt`)
で梱包するので、開発中に書いたパスがそのまま通ります。オプション指定時の
規則は次のとおりです。

- リンク先がファイルなら、その内容をリンク名のファイルとして梱包
- リンク先がフォルダなら、再帰して配下をまとめてリンク名のフォルダと
  して梱包 (隠しファイルは通常のフォルダと同じ規則で飛ばす)
- フォルダ外を指すリンクを梱包したときは **警告** を出す。再帰先
  (外部フォルダの中) で見つけたフォルダ外リンクにも同じ規則で警告を出す
- 壊れたリンク (先がない) は **警告** を出してスキップする
- 隠しファイルを指すリンクは **警告** を出す。ただしエラーで拒否する
  リンクには警告を出さない
- 同じ外部フォルダを複数のリンクが参照するときは、各リンク名の下に
  内容が揃うよう **警告** を出して重複梱包する
- 循環リンク (辿った途中で同じフォルダへ再び到達) は **エラー**

## 署名まわり（実機で確認した結果）

**追記しても署名は壊れません。むしろ `codesign` し直すと壊れます。**

macOSのad-hoc署名が守る範囲は CodeDirectory の `codeLimit` までで、
その後ろに足したバイトは対象外です。Apple Silicon機で、追記しただけの
バイナリがそのまま起動することを確認しています。

一方、追記済みのファイルを `codesign --force --sign -` にかけると、
Mach-Oの末尾に余分なデータがある状態なので
`main executable failed strict validation` で拒否され、書き換えられた
実行ファイルは起動時に SIGKILL されます（exit 137）。

したがって**署名には触らない**のが正解です。Windowsも同様に、PEローダは
末尾の余分なデータを見ません。
