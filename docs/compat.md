# 公式実装（TypeScript版）との互換性

Go版が「何をもって正しいとするか」をまとめたドキュメントです。設計の基準は
リポジトリ直下の `AGENTS.md` で、本ドキュメントはそこから互換性に関する
節を独立させたものです。

公式のTypeScript版はローカルの `./nadesiko3/` にcloneしてあるので、これを
参照して作業を行います。ただし `./nadesiko3/` は参照用の別リポジトリであり、
Go版のコミットには含めません。

**互換性を保証する範囲は `plugin_system` のみ**です。`stdlib/` がそれに
あたり、`nodelib/` など他のパッケージはGoらしく再設計してよい領域です
（→ AGENTS.md 3節）。

---

### 『尋ねる』の入力変換（plugin_node相当）

『尋ねる』は標準入力とgonako-guiのプロンプトダイアログで同じ数値変換を使います。
公式Node.js版の `plugin_node.mts` の `Number(line)` に合わせ、空入力を確定すると
数値 `0`（`TYPEOF` は `number`）を返します。空白だけの入力も数値 `0` になります。
入力を文字列のまま受け取りたい場合は『文字尋ねる』を使います。
標準入力のEOFで何も読めなかった場合は入力エラーとなり、空行の確定とは区別します。
数値変換時の空白の除去も `value.ToNumber` のJS相当の規則を使います。

これは #220・#305 で決めたGo版の方針であり、`plugin_system` の互換保証とは別です。
公式ブラウザ版の『尋ねる』は空入力を空文字列のまま返しますが、gonako-guiは
標準入力との一貫性を優先します。公式ブラウザ版の『ダイアログキャンセル値』は
キャンセル操作にだけ使われ、空入力の確定には影響しません。gonako-guiでは
『尋ねる』のキャンセル時に設定値を返し、未設定時は空文字列を返します。
『文字尋ねる』も同じ設定値を文字列にして返します（#302、[nadesiko3 #2605](https://github.com/kujirahand/nadesiko3/issues/2605)）。

## 1. 差分fixtureについて

コードより先に「何が同じなら正しいのか」を固定します。

```text
nadesiko3/core/test/fixtures/compat/
  SPEC.md              データ形式の仕様（言語非依存）
  cases/*.json         ケース定義（人が書く）
  expected/*.json      期待値。TypeScript版から自動生成
  compat_case.mjs      読み込み・実行・値の正規化
  make_compat_golden.mjs   期待値を生成する
  check_compat.mjs     別実装の結果と突き合わせ、通過率を出す
nadesiko3/core/test/compat_fixture_test.mjs   期待値が勝手に変わらないことを守る回帰テスト
```

Go版から見た使い方は次のとおりです。

```bash
# 1. ケースを読み、1件ずつ実行して SPEC.md の形式でJSONに書き出す（Go側の仕事）
gonako compat run --cases ./testdata/compat/cases --out ./out

# 2. 通過率を見る（なでしこ3リポジトリ側のツール）
(cd nadesiko3 && npm run compat:check -- /path/to/out)
#   合計: 180/236 通過 (76.3%)  不一致 56件 / 未実行 0件 / 非対応 3件 / 意図的差異 2件
```

分母の `236` は、ケース総数 `241` から `unsupported`(3件) と `intentionalDiff`(2件) を
引いた**集計対象の件数**です。ケースを足せばこの数は動きます。

fixtureは `scripts/sync-compat-fixtures.sh` で本家からコピーし、コピー元の
コミットを `testdata/compat/SOURCE` に記録する。`cases/` と `expected/` を
手で片方だけ更新しないこと。

**この通過率が、開発中ずっと唯一の進捗指標になります。** 実装 → 実行 → 通過率、
という短いループが回るので、コーディングエージェントに任せられる形になります。

## 2. 文字列 --- Goネイティブ（UTF-8 / rune基準）

**Go版の文字列はGoの `string`（UTF-8）をそのまま使い、UTF-16互換層は作りません。**

当初はUTF-16互換層が必要だと考えていましたが、現行のTypeScript版を調べたところ、
`core/src/plugin_system_string.mts` の文字列命令は**すでに `Array.from` ベースで
コードポイント単位に揃えられていました**（`String.fromCodePoint` / `codePointAt` も同様）。
つまりサロゲートペアを考慮した実装になっており、**Goのrune基準とそのまま一致します。**

実測で確認した対応状況です（`"𩸽あ"` などで検証）。

| 命令 | TS版 | Go版(rune基準) | |
|---|---|---|---|
| `文字数` / `文字抜出` / `文字左部分` / `文字右部分` | コードポイント単位 | 同じ | ○ 一致 |
| `文字検索` / `何文字目` / `文字挿入` / `文字削除` | コードポイント単位 | 同じ | ○ 一致 |
| `文字列分解` | コードポイント単位 | 同じ | ○ 一致 |
| `置換` / `単置換` / `出現回数` | `split`/`join` ベース | 同じ | ○ 一致（注1） |
| `ASC` / `CHR` | コードポイント値 | 同じ | ○ 一致 |
| `ゼロ埋` / `空白埋` / `カタカナ半角変換` | コードポイント単位 | 同じ | ○ 一致（注2） |
| ZWJ絵文字 `"👨‍👩‍👦"` の `文字数` | 5 | 5 | ○ 一致 |

注1: これらは内部的にはUTF-16のまま部分文字列を突き合わせますが、
部分文字列の一致判定と分割は**コードユニットで数えてもコードポイントで数えても
結果が変わらない**ため、Goの `strings.Replace` / `strings.Count` と一致します。

注2: `ゼロ埋` / `空白埋` は桁数を `v.length`（UTF-16コードユニット数）で、
`カタカナ半角変換` は `s.split('')`（コードユニット分割）で数えていたため、
本来ここはrune基準と食い違う箇所でした。**本家TS版で修正され、fixtureも
再同期済み**です（サロゲートペアのケースが追加されています）。

### 一致しない1点

Goネイティブにすると差が出るのは、**次の1つ**です。
差分fixtureで `intentionalDiff` を付けて集計から外してあります。

| 箇所 | TS版 | Go版 | 備考 |
|---|---|---|---|
| 正規表現の `.` など | サロゲートを2文字扱い | 1文字扱い | JSは `u` フラグなしのため |

これは**サロゲートペア（BMP外の文字）を含む文字列に限った話**で、
日本語の常用範囲・絵文字の`文字数`では差が出ません。

> **「1つ」は現時点の調査結果であり、証明ではありません。**
> 上の注2のように、TS版の `plugin_system_string.mts` には
> `.length` / `split('')` / `substring` を使った命令が残っていることがあります。
> 新しいUTF-16依存が見つかったら、**まず本家側を修正して**サロゲートペアの
> ケースをfixtureに足し、Go版はrune基準のまま追随する、という順序で進めます。
> Go版に合わせて `intentionalDiff` を増やすのは最後の手段です。

> **文字コード変換（`ASC`/`CHR`）で差が出るのでは、という懸念について。**
> ここは逆に**既に一致しています。** TS版が `codePointAt` / `fromCodePoint` を
> 使っているため、`("𩸽"のASC)` は `171581`（コードポイント値）を返します。
> UTF-16のコードユニット値（`0xD867`）ではありません。

### 1点への対処

- **正規表現**: Goの `regexp` はrune基準なので、意図的差異とします。
  JSの `u` フラグ付き正規表現と同じ挙動になります

> かつては文字列の添字アクセス `A[0]` も差異の一つでした（TS版がサロゲートの
> 片割れを返していた）。本家TS版が文字列の添字アクセスをコードポイント単位で
> 実装したため（#2590）、この差はなくなっています。

> かつては `要素数` / `LEN` も差異の一つでした（`"𩸽あ"` に対して
> `文字数` が2、`要素数` が3を返していた）。本家TS版がコードポイント基準に
> 揃えたため（#2449）、この差はなくなっています。

### 実装上の注意

Goの `string` は**UTF-8バイト列**なので、`len(s)` はバイト数、
`s[i]` はバイトを返します。なでしこの命令で使ってよいのは次だけです。

```go
// internal/value/text
func RuneLen(s string) int              // utf8.RuneCountInString
func RuneSlice(s string, i, j int) string
func RuneAt(s string, i int) string
```

**`len()` と `s[i]` を直接使わない**ことを、コードレビューの観点に入れてください。
ここを間違えると、日本語を含むほぼ全ての文字列でバグります。

## 3. エラー

エラーの**種類・行番号・文面**が互換対象です。

```go
// internal/errs
type Kind int   // Lexer / Syntax / Runtime

type NakoError struct {
    Kind Kind
    File string
    Line int      // 0起点。文面では +1 して「N行目」と出す
    Msg  string
}

func (e *NakoError) Error() string   // "[実行時エラー]main.nako3(1行目): ..."
```

`compat run` の出力する `error.type` は**TS版のクラス名**なので、
`Kind` から次のとおり変換します。文面の接頭辞とは別物なので混同しないこと。

| `Kind` | `error.type` | `Error()` の接頭辞 |
|---|---|---|
| `Lexer` | `NakoLexerError` | `[字句解析エラー]` |
| `Syntax` | `NakoSyntaxError` | `[文法エラー]` |
| `Runtime` | `NakoRuntimeError` | `[実行時エラー]` |

`Msg` は改行を含みうる（`09_error` の「閉じ括弧なし」は2行の文面を返す）ので、
1行だと決め打ちしないこと。

差分fixtureの `09_error` グループが、この文面をそのまま固定しています。
文面の日本語は現行TS版からの**逐語移植**であり、Go版で言い回しを改善しないでください。

## 4. 本家リポジトリ（TypeScript版）側でやること

- DocTestや差分fixtureの調査中に、**本家TypeScript版の命令実装ミス・仕様との不一致・
  回帰不具合を見つけた場合は、Go版だけで回避せず、再現コードと期待結果・実際結果を添えて
  [なでしこ3のIssues](https://github.com/kujirahand/nadesiko3/issues) に投稿する**
- 差分fixtureを**育てる**。互換で困ったケースが見つかるたびに `cases/` へ足す
- **UTF-16依存が見つかったらTS版側を直す**（`ゼロ埋` / `空白埋` /
  `カタカナ半角変換` は修正済み）。直したらサロゲートペアのケースを `cases/` に足し、
  Go側は `scripts/sync-compat-fixtures.sh` で**再同期して `SOURCE` を更新する**。
  同期を忘れると、Go版が正しいのに不一致として数えられます
- 期待値を変える変更（挙動の変更）は、**変えた理由をコミットメッセージに残す**。
  Go側は理由が分からないと追随できません
- `plugin_system` に命令を足したら、対応するケースも足す

差分fixtureは、**Go版の計画が途中で止まってもTS版の回帰テストとして残る資産**です。

## 5. CSV（plugin_csv）の本家との差異（互換保証の対象外）

`csvlib` は互換保証範囲である `plugin_system` の外である。ただし、本家の
`nako_csv.mts` を移植した実装であり、境界ケースは Issue #373 で本家との実測照合を行った。

TSV取得では、末尾タブの後にある空セルが落ちる不具合があった。原因は末尾トリムが区切り文字まで削除していたことであり、Issue #373 で本家に合わせて修正した。

Go版として固定している差異は次のとおりであり、いずれも `parse_edge_test.go` でテストとして固定している。

1. `float64` の範囲外となる指数表記（例: `1e400`）は、本家では `Infinity` になるが、Go版では文字列のまま扱う。
2. BOM（U+FEFF）は、本家では先頭セルから除去されるが、Go版では先頭セルに残る。
3. 全角空白（U+3000）は、本家ではセル先頭から除去されるが、Go版では残る。Go版のトリム対象はASCII空白のみである。
4. 空白だけの行は、本家では空白と改行がまとめて除去されて行ごと消える。区切り文字直後の「空白+改行」では、本家は同じ理由で前後の行が連結する。Go版では改行を行終端として扱うため、どちらも空セル1個の行として残る（`parse_edge_test.go` の TestParseEdgeNewlines「空白だけの行」で固定）。

主な一致仕様として、閉じていない引用符以降は捨てられること、閉じ引用符の直後が区切り文字または改行でない場合は結果が空になること、先行ゼロを持つ `007` は数値化されること、行中にあるセルの末尾空白は残ることを確認している。

なお `CSV変換`→`CSV取得` の往復には、空セルだけの行が末尾にあると行が畳まれる等の既知の差分があり、`parse_roundtrip_test.go` で固定している。往復のプロパティテストでは、この差分に当たる入力（単一の空セル行）を生成対象から外している。

## 6. 文字コードと形式変換の既知の差分

`plugin_system` の外（`nodelib` の `エンコーディング変換` / `エンコーディング取得` など）の挙動である。
互換保証の対象外だが、現行挙動を次のテストで固定している。

- `internal/vm/data_conversion_test.go`
- `internal/vm/data_conversion_encoding_test.go`
- `internal/nodelib/encoding_property_test.go`

### 6.1 BOM

- UTF-8 と `utf-16le` の復号では、BOM（U+FEFF）は取り除かれず、先頭に残る。CSV/TSVにすると先頭セルの頭に付く。
- `utf-16` を指定したときだけ、BOMを解釈してLE/BEを判別し、結果からBOMを取り除く。
- `utf-16` への変換はBOM付きのBE（先頭 `FE FF`）で出力する。`utf-16le` への変換はBOMを付けない。
- Excelの「Unicodeテキスト」（UTF-16LE + BOM、タブ区切り）は、`utf-16` で `エンコーディング取得` してから `TSV取得` すると表になる。

### 6.2 SJIS変換できない文字

`SJIS変換` と `エンコーディング変換`（`shift_jis` など）は、Shift_JISに無い文字をエラー（`rune not supported`）にする。
波ダッシュ（U+301C）、U+2212、絵文字、`𠮷`（U+20BB7）が該当する。Windowsのcp932実装とは差異がある。

### 6.3 cp932 の重複コード

cp932 には同じ文字に複数のコードが割り当てられた範囲（NEC特殊文字・NEC選定IBM拡張・IBM拡張の重複）がある。復号はどちらのコードからも同じ文字になるが、再エンコードすると正規側のコードで出力されるため、バイト列としては往復しない。実測で重複コードは 398 件（FAxx・FBxx の全域、FC40〜FC4B、87xx の一部記号、EEF9）あり、`encoding_property_test.go` で範囲と件数を固定している。意味（文字列）としての往復は全件一致する。また単一バイト 0x80 は制御文字 U+0080 に復号されるが符号化できない。

### 6.4 不正なバイト列

SJIS・EUC-JP・UTF-8のいずれで復号しても、不正なバイト列はエラーにならず、U+FFFD へ置換される。
置換の単位は系列によって異なる（`FF FF FF` は U+FFFD が3つになるが、UTF-8 の途中で切れた3バイト文字は全体で1つ、オーバーロングな `C0 AF` はバイトごとに1つずつ）。代表ケースは `TestEncodingGetInputs` で固定している。

### 6.5 形式間の変換（CSV / JSON / TOML）

| 項目 | 往復で保たれるか |
|---|---|
| CSV: 数値らしいセル | 数値へ自動変換される（文字列 `"1"` と数値 `1` の区別は失われる） |
| CSV: カンマ・引用符・改行を含むセル | 保たれる |
| CSV: 空セルだけの行が末尾にある | 行が畳まれる（§5） |
| JSON: 文字列・数値・真偽値・null・入れ子 | 保たれる（2^53 を超える整数は float64 に丸められる） |
| JSON: ±Inf / NaN | `null` になる（TOMLの `inf` / `nan` を JSON にした場合） |
| TOML: null | 空文字列になる（TOMLにnullが無いため） |
| TOML: 日時（日時・日付・時刻の4種） | 文字列になる |
| JSON整形・TOMLエンコードのキー順 | 保たれない（実装依存。値で比べること） |
